# 可信研究報告規格

## 1. 目的

可信報告不是「看起來完整的文章」，而是可檢查、可追溯、可更新的研究產物。讀者應能回答：

1. 報告試圖回答什麼問題？
2. 結論依據哪些證據？
3. 來源是否適合支持該主張？
4. 哪些部分仍不確定？
5. 新資訊出現時，哪裡需要更新？

## 2. 必要章節

### 2.1 報告摘要

- 研究題目與用途。
- 3 至 7 個關鍵發現。
- 整體可信度：`high`、`medium` 或 `low`。
- 資料截止時間與報告產生時間。

### 2.2 研究範圍

- 核心問題與子問題。
- 包含與排除範圍。
- 地區、語言、時間範圍、目標受眾。
- 已知限制，例如付費牆、登入限制或缺乏公開資料。

### 2.3 方法

- 搜尋關鍵字與查詢策略。
- 使用的資料來源類型。
- 來源篩選、去重與排除規則。
- 評估可信度的方法。

### 2.4 關鍵發現

每個發現必須包含：

- `claim_id`：穩定且唯一，例如 `C-001`。
- 主張內容。
- 類型：`fact`、`inference`、`recommendation` 或 `unknown`。
- 重要程度：`critical`、`supporting` 或 `context`。
- 支持來源的 `source_id`。
- 反對或限制該主張的來源。
- 主張可信度與簡短理由。

### 2.5 衝突、未知與限制

- 不同來源的衝突點。
- 無法確認的資訊。
- 證據可能存在的偏差。
- 哪些結論不能由現有資料推出。
- 每一個衝突與未知事項都需放入解決矩陣，標示 `resolved`、`partially_resolved` 或 `open`。
- 解決矩陣需列出判斷、解決方式、依據來源、下一步與可驗證的關閉條件。
- 可由定義、範圍或決策規則收斂的衝突，應直接記錄決策；需要 PoC、benchmark 或組織政策選擇的未知，不可在缺少證據時標成已解決。

### 2.6 結論與建議

- 結論需對應研究問題。
- 建議必須與事實分開呈現。
- 建議需標示適用條件與風險。
- 建議需拆分成「可實作性」與「未來性」。
- 可實作性需列出目的、可採用的技術組合、實作流程、最小交付物、驗收標準、依據來源與後續研究提示詞。
- 未來性需列出當前缺點、演進方向、啟動條件、依據來源與後續研究提示詞。
- 後續研究提示詞應可直接交給 agent，用來補足技術選型、流程細節或 benchmark 證據。
- 對需要落地的技術研究，需另外提供開源工具選型：只使用一個開源工具時的前三種推薦，以及多個開源工具配合時的前三種推薦。
- 單一工具推薦需列出排名、推薦理由、適用情境、主要能力、必須接受的缺口與最小導入方式。
- 多工具推薦需列出排名、工具組合、角色分工、整合流程、推薦理由、取捨、最小交付物與驗收標準。
- 推薦排名必須揭露適用條件，不可暗示任何單一工具能覆蓋完整 assurance architecture。

### 2.7 來源導航與獨立目錄

Markdown 報告不需要內嵌所有來源 metadata。應提供來源數量摘要，以及連到獨立來源總目錄與完整 JSON 報告的連結。來源總目錄負責提供 `S-001` 到最新來源的導航、層級與大綱。

結構化 JSON 報告與每個來源的 `source.json` 至少包含：

- `source_id`：穩定且唯一，例如 `S-001`。
- 標題、URL、發布者、作者或機構。
- 若來源會持續更新，記錄可重現證據的永久連結、版本、tag、commit SHA 或頁面定位資訊。
- 保存本地 snapshot 路徑、SHA-256 `content_hash`、`freshness.mode` 與必要的 `recheck_after`。
- 發布日期、最後更新日期與擷取日期。
- 來源類型與證據層級。
- 支持哪些 `claim_id`。
- 品質備註與潛在利益衝突。

## 3. 證據層級

| 層級 | 說明 | 常見例子 |
| --- | --- | --- |
| `A` | 可直接支持主張的第一手證據 | 官方資料、法規原文、原始研究、公司財報、公開資料集 |
| `B` | 有編輯或專業審查的可靠二手來源 | 同行評審綜述、政府說明文件、具透明方法的研究機構報告 |
| `C` | 可用於線索或補充脈絡的二手來源 | 主流媒體、專業媒體、具署名與引用的文章 |
| `D` | 僅作線索，不應單獨支持重要結論 | 未驗證貼文、論壇、匿名內容、缺少方法或來源的文章 |

重要結論優先使用 `A` 或 `B` 級來源。若只能取得 `C` 或 `D` 級來源，必須降低可信度並明確揭露。

「官方」不會自動等於 `A` 級。官方首頁、行銷頁面或未固定版本的文件可能只能提供背景資訊。來源是否為 `A` 級，仍取決於它是否直接、精確且可重現地支持該主張。

### 3.1 GitHub 與持續更新文件

技術研究常使用 GitHub repository、官方文件與 release note。這些來源應額外處理版本定位：

| 來源 | 建議用途 | 記錄方式 |
| --- | --- | --- |
| 官方版本化文件 | 說明特定版本的行為、設定或介面 | 記錄文件版本、頁面 URL 與章節定位 |
| GitHub 原始碼或設定檔 | 驗證實作細節 | 使用指向 commit SHA 的 permalink，記錄檔案路徑與行號 |
| Release note、changelog、tag | 驗證版本變更與發布內容 | 記錄 release 或 tag URL、版本與發布日期 |
| GitHub issue、discussion、pull request | 補充背景、已知問題或設計討論 | 預設視為輔助證據；除非主張本身就是「此討論存在」 |
| Repository README 的預設分支版本 | 快速理解專案 | 可作線索；重要結論需改用固定 commit 或版本文件 |

若找不到固定版本連結，至少記錄 `retrieved_at`、頁面定位資訊與內容雜湊，並在限制中揭露來源可能變動。

## 4. 主張可信度

每個關鍵主張都要標示：

| 等級 | 判斷條件 |
| --- | --- |
| `high` | 有直接且相關的 `A` 級來源，或多個彼此獨立且一致的高品質來源 |
| `medium` | 證據方向一致，但存在範圍限制、二手轉述或部分不確定性 |
| `low` | 來源不足、來源品質偏低、存在重大衝突，或只能合理推測 |

不得用來源數量取代來源品質。十篇轉載同一篇新聞仍視為單一證據鏈。

## 5. 可追溯性規則

- 關鍵主張必須至少連到一個來源。
- 每個來源的 `supported_claim_ids` 必須回指其支持的主張，並與主張的 `supporting_source_ids` 對稱。
- 數字、日期、排名、法律狀態與「最新」資訊必須附來源與擷取日期。
- 推論必須標成 `inference`，並說明推論依據。
- 引用原文需短且必要；預設以摘要與轉述呈現。
- 不得引用未實際讀取或無法確認內容的網址。
- 來源不可只記錄搜尋結果摘要，應記錄最終頁面或原始文件。
- 對會持續更新的文件，關鍵主張優先引用永久連結或固定版本。
- 引用 GitHub 預設分支內容時，應解析並保存 commit SHA；引用程式碼時加上檔案路徑與行號。

## 6. 來源品質檢查

每個來源都要評估：

- **Authority**：作者或機構是否具權威性？
- **Directness**：是否為原始資料？是否直接支持主張？
- **Recency**：時效是否符合研究問題？
- **Transparency**：是否揭露方法、樣本、資料與限制？
- **Independence**：是否與其他來源獨立？是否只是轉載？
- **Conflict of interest**：發布者是否可能從特定結論獲益？
- **Reproducibility**：日後能否讀取與報告撰寫時相同的版本？

## 7. 報告整體可信度

整體可信度不是所有主張的平均值。若核心結論依賴低可信主張，整體報告不得標為 `high`。

建議計分：

| 面向 | 比重 |
| --- | ---: |
| 關鍵主張的來源覆蓋率 | 30 |
| 第一手或高品質證據比例 | 25 |
| 雙向可追溯性、snapshot 與引用完整度 | 20 |
| 衝突、未知與限制處理 | 15 |
| 新鮮度與可重現性 | 10 |

`quality_score` 是 evidence-aware 分數，用於檢查，不應製造虛假的精確感。`structural_score` 只表示必要欄位與章節是否齊全，不可取代證據品質。報告仍需以文字解釋可信度理由。

## 8. 最低發布門檻

報告在發布前必須符合：

- 所有 `critical` 主張都有來源。
- 所有數字、日期與時效性主張都有來源。
- 已列出資料截止時間。
- 已檢查重複來源與單一證據鏈。
- 主張與來源之間的雙向 backlinks 一致。
- 已列出重大衝突與未知事項。
- 已區分事實、推論與建議。
- 所有來源 URL 可供讀者追溯。
- 依賴持續更新文件的 `critical` 主張已保存固定版本；無法固定版本時，至少保存 snapshot hash、`recheck_after` 並揭露限制。
